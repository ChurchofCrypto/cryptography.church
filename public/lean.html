Proving the Alberti Disk

The coin's cipher, written in Lean 4, a programming language that checks mathematical proofs. In the workshop we prove that the disk always decrypts what it encrypts, for every key and every message. Then we prove, just as carefully, that it is broken. Here are the theorems with a demo of each, the proofs one step at a time, and the exercises to try in your browser.

Drag the disk to turn it. Click a cell in the message to see it on the coin.

A test and a theorem

A test checks one input. This line in the workshop runs on every build:

#guard encrypt 'D' "HELLO40C3" == some "Dθsooσnzux"

It tells you about HELLO40C3 under D, and nothing else. A theorem is a claim about every input. Lean accepts one only with a proof, and checks every step of that proof down to its basic rules. If the proof skips a case, Lean says so.

Theorem 1 · Exercise 3.4

Decryption undoes encryption

For every key letter and every message: if encryption succeeds, decrypting the result gives the message back.

theorem decrypt_encrypt {key : Char} {msg ct : String}
    (h : encrypt key msg = some ct) : decrypt ct = some msg

In Lean, encryption returns an Option: some ciphertext, or none if a letter is not on the ring. The hypothesis h says it succeeded.

Theorem 2 · Exercises 1.1 to 1.3

The disk is a permutation

No symbol is printed twice, and turning the disk back undoes turning it forward. So under any setting, each of the 36 letters is paired with exactly one symbol, and each symbol with exactly one letter.

theorem disk_injective : Function.Injective disk

theorem decIdx_encIdx : ∀ s i : Sym, decIdx s (encIdx s i) = i

Both are proved by decide: Lean checks all 36 × 36 = 1296 cases. That is a proof, not a test, because the statement has only finitely many cases and Lean checks each one.

Step through the proof

On the coin each letter sits right over its symbol, so the lines are short and straight. Sort the inner ring and the same pairing becomes a tangle, but it is still one line per letter and one per symbol. Hover or tap a letter, or focus the picture and use the arrow keys.

Theorem 3 · Exercise 4.2

…so equal letters give equal symbols

Under one setting, two places in the ciphertext carry the same symbol if and only if the message has the same letter there. Every double letter, every repeat and every letter count survives encryption. This is the bad news, proved with the same care.

theorem encSyms_eq_iff (s : Sym) (m : List Sym) (i j : Nat)
    (hi : i < (encSyms s m).length) (hj : j < (encSyms s m).length) :
    (encSyms s m)[i] = (encSyms s m)[j] ↔ m[i] = m[j]

Here a message is a list of ring cells, so nothing can fail. The bounds hi and hj just say that i and j are positions in the message.

Theorem 4 · Exercise 4.4

Trying all 36 settings always works

Even if the key letter were kept secret, the real message is among the 36 candidates you get by trying every setting. And there are exactly 36 settings.

theorem brute_force_complete (s : Sym) (m : List Sym) :
    ∃ s' ∈ List.finRange 36, decSyms s' (encSyms s m) = some m

theorem keyspace_size : (List.finRange 36).length = 36

The proof is one line: the right setting s' is the one that was used. Lean does not need to know which line is English. It only proves that the message is in the list. Picking it out is easy: here a letter-frequency score does it.

Correct is not secure

    
What these proofs do not say

    

      
A proof covers its statement, nothing more

        
Theorem 1 says that decryption works. It never mentions an attacker, so it cannot tell you anything about one. When you read
          “formally verified”, ask what exactly was stated.

      
The same rigour proves the attack

        
Theorems 3 and 4 are as solid as Theorem 1, and they are bad news: equal letters stay equal, and 36 tries always find the message.
          Formal methods prove attacks as readily as defences.

      
Security is a game

        
A security statement pits a challenger against an adversary and bounds the adversary's advantage. For the one-time pad that
          advantage is exactly zero: perfect secrecy, which can be proved outright.

      
Real ciphers rest on assumptions

        
For AES or X25519 the claim is that no efficient adversary wins. Nobody can prove that today; it would settle P versus NP.
          What gets proved are reductions: break this, and you break that hard problem. Lean can check the reduction, not the hardness.

    

    

      
On the coin there is not even a secret to protect: the disk order is printed on every coin and the key letter travels in clear.

How this page was made

    

      

        
The goals in the stepper come from Lean itself. A script opens the answer key in the Lean language server, the same program
          behind the VS Code goal view, and asks for the goal at the end of each line of each proof. It stops if the file has any error.

        
The theorems are checked by lake build on Lean 4.35.0. #print axioms lists at most Lean's three standard
          axioms (propext, Classical.choice, Quot.sound), so no proof is skipped and no computation is trusted blindly.

        
The demos run a second copy of the cipher, in JavaScript. It is not proved, so it checks itself against the workshop's
          test vectors every time this page loads.
